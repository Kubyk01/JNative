TestHeap.exe performance investigation, round 2  (2026-11-06)
=============================================================

Result: 688 ms for 10,000,000 iterations (before ArrayCoAllocator: 671 ms). No change.

1. Why the time did not improve: ArrayCoAllocator never fires
-------------------------------------------------------------
Evidence:
- target/target/generated-jnative/TestHeap$Payload.ll still has `call i8* @calloc` for the
  byte[] in Payload.<init>, and storePayload still callocs only sizeof(Payload) and frees
  two pointers (padding, then the object). So the hot path is the same as before.
- I regenerated the IR with the current jar (`analyze ... --no-compile`, in a scratch dir)
  and got the same result. The jar does contain ArrayCoAllocator.class.
- I debugged it live with jdb (bundled with the JDK; nothing installed): a breakpoint in
  ArrayCoAllocator.findCandidate, then evaluating each condition for TestHeap$Payload:
    reflectClasses.contains("TestHeap$Payload")  = true   <-- the rejecting check
    reflectClasses.size()                        = 4171   (practically every reachable class)
    mentionedByIndy                              = false
    access = 48 (final), super = java/lang/Object, interfaces = [], one <init>(JI)V, no <clinit>
    padding: final [B; NEW sites of Payload = 1
    the ctor IR has exactly the expected shape:
      t1 = STATIC_CALL Math.max(II)I 0, param3
      t2 = NEW_ARRAY t1, byte
      PUT_FIELD this, TestHeap$Payload.padding, t2
      then only GET_FIELD -> ARRAYLENGTH / ASTORE on padding
    findCandidate("TestHeap$Payload") = null

Root cause:
  MethodBytecodeVisitor (around lines 1124-1140) calls reflectInfo.getOrCreateClassInfo(cls)
  for EVERY reachable class as soon as Method.invoke or Constructor.newInstance is reachable,
  and the JDK bootstrap always reaches them. ReflectInfo.getAllClasses() is the keySet of that
  map, so "class is in ReflectInfo" means nothing, and the guard
      if (reflectClasses.contains(className) ...) return null;
  in ArrayCoAllocator.findCandidate rejects every class.

Fix (code change, not made here):
  Reject only when reflection can really construct the object or reach the field:
  - Pass ReflectInfo (not getAllClasses()) to ArrayCoAllocator.
  - Reject C when getOrCreateClassInfo(C).getConstructors() is non-empty: the reflection
    adaptor (LlvmGlobalEmitter.emitAdaptorForConstructor) allocates only objectSize bytes,
    so the ctor would then write the array past the end of the object.
  - Reject C when getFields() contains the co-allocated field (Field.get could leak the
    interior pointer).
  - An empty ReflectClassInfo (the normal case, created by the loop above) is safe.
  Note: using getOrCreateClassInfo creates entries as a side effect. That is harmless after
  reachability has finished, or add a plain lookup getter.

Expected gain once it fires: one fewer calloc and one fewer free per iteration, which is
about 1/4 to 1/3 of the per-iteration heap time. Roughly 690 ms -> 500-550 ms (estimate,
not measured).

2. Where the time goes (unchanged from round 1, same binary shape)
------------------------------------------------------------------
lldb sampling (default run, main thread, _NO_DEBUG_HEAP=1):
  ~35%  RtlAllocateHeap (+ LFH internals, memset)   <- 2x calloc per iteration
  ~27%  RtlQueryPerformanceCounter                    <- System.nanoTime() every iteration
  ~15%  RtlFreeHeap / HeapFree                        <- 2x __jnative_free per iteration
  ~10%  TestHeap.exe own code
  ~13%  startup (thread creation, DLL loading, CrowdStrike hooks)

Suggestions, by size of win:
  a) Fix the ArrayCoAllocator reflection guard (above). Small change, removes 1 alloc + 1 free.
  b) Faster small-object allocator: per-thread size-class free lists in jnative_runtime.c,
     or link mimalloc (suggest: `vcpkg install mimalloc`). Biggest remaining win (~2x).
  c) jn_now_monotonic_win (jnative_platform.c): QueryPerformanceFrequency is called on every
     nanoTime. Cache it, and skip the timespec round-trip in
     __jnative_fn_java_lang_System_nanoTime___J (Object.c).
  d) Codegen: redundant null checks on `this` in constructors; Math.max as a real call.
